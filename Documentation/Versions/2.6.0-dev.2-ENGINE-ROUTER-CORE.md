# IA-TB 2.6 — Engine → Router CP/1 → Core (candidat DEBUG)

## Parcours technique ajouté

1. L'adaptateur partagé `App/Core/Communication/component_cp1_adapter.js` fournit une lecture authentifiée de `Functions.json` à l'adresse `GET <cpPath>/functions`. Le catalogue est lu à chaque demande, donc ses mises à jour deviennent visibles sans redémarrer le module d'adaptation.
2. Le Router `App/Core/Router/router.js` expose `GET /communication/v1/functions/:engine` derrière le secret CP/1 existant. Il sélectionne une **destination prédéfinie** dans son registre, utilise uniquement loopback et vérifie que le nom de l'Engine retourné est correct.
3. Le client `cp1_client.js` autorise cette lecture **uniquement** pour un nom d'Engine valide.
4. Le Core `sync_service.js` récupère chacun des catalogues via ce chemin CP/1, compare le contenu et actualise le gestionnaire SQLite et le cache RAM.
5. En cas d'indisponibilité, le Core conserve sa base, journalise une erreur et retente au cycle suivant ; aucune fonction inconnue ou nouvelle n'est autorisée par défaut.

## État exact

**Le pull à travers Engine → Router → Core est implémenté dans le code candidat**, mais pas encore qualifié sur tous les Engines de l'application. Le contrôle d'identité repose actuellement sur le token CP/1 partagé, l'endpoint loopback fixé par le Router et la correspondance de l'identifiant déclaré. Ce n'est pas encore une authentification cryptographique par Engine distincte.

**Non terminé :** notification push instantanée à chaque changement de manifest, outbox et ACK, preuve d'origine de chaque Engine, tests end-to-end sur tous les services, déploiement GEN-1. Certains services peuvent nécessiter une adaptation de leur serveur HTTP afin d'exposer la nouvelle route ; les catalogues Core et Router restent à gérer par un mécanisme propre, non par l'adaptateur Engine. Les tests CI n'ont pas encore été confirmés.

Cette fonctionnalité est opt-in depuis Core sous `IATB_FUNCTION_REGISTRY_SYNC_V26=1`, avec `IATB_FUNCTION_REGISTRY_DB` pointant vers un chemin SQLite privé et absolu. Le mode Direct IA Trading reste désactivé.

## Contrats exemple

- `marketdata.candles` : `symbol`, `timeframe` ; retour pas encore qualifié.
- `risk.gate.evaluate` : évaluation du risque ; pas une autorisation de négociation.
- `trading.execute` : commande à effet de bord, DENY par défaut et soumise au Risk Engine.

Tout manifeste contient `verified_handler=false` tant qu'il n'a pas été audité. Aucune déclaration de fonction n'est directement exécutable.
